## 一、项目概述

### 1.1 定位
将 `.docx` 文档（及图片）自动转换为 Adobe InDesign 排版文件 (`.indd`)。运营同学只需把文档放入输入目录，运行批处理即可。

### 1.2 核心流程

```
.docx / 图片  →  Python解析  →  JSON数据  →  InDesign排版  →  .indd文件
```

## 四、完整流水线详解

### 4.1 Python 解析阶段（docx_list_to_json.py）

**功能**：读取 `C_inputs/` 下所有 `.docx`，提取文本和图片，输出结构化 JSON。

**输入**：`C_inputs/{板块名}/*.docx`  
**输出**：`B_outputs/{板块名}/{文档目录}/output.json` + `B_outputs/_shared_images/` 图片文件

**关键行为**：
- 每篇文档独立输出一个 `output.json`
- 从 docx（ZIP）中解压 `word/media/` 提取图片
- 4_一句话 板块支持"图片模式"：从图片目录读取每张图生成 image+text 元素对
- 文本处理规则：
  - 周边板块：`■` 前自动换行
  - 新衣披露：截断"相关视频"关键词后的内容
- 板块名 → 模板 ID 映射：默认同名，支持 `doc_template_map` / `section_template_map` 覆盖

### 4.2 队列系统

任务文件 `dispatch_{timestamp}.json` 内容示例：
```json
{
  "task_type": "dispatch_all",
  "created_at": "20260611_052100",
  "source": "tauri_console"
}
```

四个状态目录：`pending/` → `running/` → `done/` 或 `error/`

### 4.3 Watcher（InDesign 启动监视器，230行）

- 注册为 InDesign `idleTasks`，每秒检查一次 `pending/` 目录
- 取最旧任务 → 移至 `running/` → `$.evalFile(create_layout_dispatch.jsx)`
- 成功 → 移至 `done/`，失败 → 移至 `error/` 并记录错误
- 使用 `#targetengine "autoRainbowWatcherEngine"` 保持常驻
- 每 10 秒写入心跳文件 `queue/.watcher_heartbeat`，供前端检测存活状态
- 清理同名旧 watcher 实例，防止重复注册

### 4.4 Dispatch（分发调度器，759行）

- 扫描 `B_outputs/` 下所有 `output.json`
- 读取 `A_templates/{板块}/config.json` 确定 `layout_script`
- 打开模板 `.indd`，通过 `app.scriptArgs` 传参，eval 对应排版脚本
- 保存 `.indd` 到文档目录
- 打开模板后自动更新过期链接（`updateOutdatedLinksQuietly`）
- 非 batch 模式下显示进度 UI 窗口（进度条 + 状态文本）
- 实时写入 `queue/progress.json` 供前端读取
- 完成后弹窗询问是否打开所有生成的 `.indd`

### 4.5 排版引擎（create_layout_templateA.jsx）

核心引擎（2467行），支持四种模式：
- **templateA**：标准图文纵向排列
- **templateB**：一句话模式，图片+文本成对，间插装饰卡片
- **templateC**：新衣披露模式，标题区+图文+相框区（`photo_group`）
- **templateD**：周边模式，双页双模板（3×3 网格 + 纵排图文）

分页策略：soft/hard 双阈值（`content_bottom_soft` / `content_bottom_hard`）

原型框体系（通过脚本标签 label 定位）：
- `body_text_proto_label`（默认 `proto_text`）
- `body_image_proto_label`（默认 `proto_image`）
- `main_heading_label`（默认 `main_heading`）
- `sub_heading_label`（默认 `sub_heading`）
- `title_image_label`（默认 `title_image`）
- `column_space_label`（默认 `column_space`）

## 五、InDesign 脚本执行标准与逻辑

### 5.1 ExtendScript 基础

InDesign 脚本使用 **ExtendScript**（Adobe 自家的 JavaScript 方言，基于 ES3），文件后缀为 `.jsx`。

关键指令：

| 指令 | 作用 | 当前使用 |
|------|------|---------|
| `#target "InDesign"` | 声明脚本目标应用。无此指令时，脚本只能在已运行的 InDesign 进程内被 eval | **⚠️ 已在 InDesign 2026 中失效**，脚本静默不执行。所有 `.jsx` 中已移除 |
| `#targetengine "xxx"` | 创建/使用持久化 ExtendScript 引擎。脚本执行完后全局变量和事件监听不被销毁 | watcher 使用 `"autoRainbowWatcherEngine"`。其他脚本无需此指令 |
| 无 target 指令 | 脚本在默认引擎中运行，执行完毕即销毁 | dispatch、templateB/C/D 使用此方式（通过 `$.evalFile` 被加载） |

### 5.2 脚本类型与安装位置

| 类型 | 目录 | 执行时机 | 适用场景 |
|------|------|---------|---------|
| **Startup Scripts**（启动脚本） | `~/Library/Preferences/Adobe InDesign/Version*/<lang>/Scripts/Startup Scripts/` | InDesign 启动时自动执行 **一次** | watcher（需要常驻监听队列） |
| **Scripts Panel**（面板脚本） | `~/Library/Preferences/Adobe InDesign/Version*/<lang>/Scripts/Scripts Panel/` | 用户从脚本面板双击手动执行 | 可以放调试/工具脚本 |
| **临时脚本** | 任意位置 | 通过 `$.evalFile()` 或 AppleScript 的 `do script` 加载执行 | dispatch、template 脚本 |

> **重要：** Startup Scripts 只在 **InDesign 启动时** 加载执行。在 InDesign 运行中安装/修改脚本后，必须重启才生效。  
> 某些 InDesign 版本（如 2026）的"启用启动脚本"偏好设置可能已移除或被重置，导致所有 Startup Scripts 静默不执行。

### 5.4 Persistence 机制详解

**`#targetengine` vs `$.global` vs idleTask 三者的关系：**

```
#targetengine "autoRainbowWatcherEngine"
  └── 创建一个命名引擎，脚本执行完不销毁
       └── $.global.__AUTO_RAINBOW_WATCHER_INSTALLED__ = true
             └── 防止重复初始化（引擎若已存在，直接 return）
        └── app.idleTasks.add({ name: "AutoRainbowDispatchWatcher", sleep: 1000 })
            └── 注册 idle task，每 1000ms 回调一次 handler
                 └── handler 检查 pending/ 目录 → 有任务则处理
```

**关键点：**
- 没有 `#targetengine` → idle task 会在脚本执行完后被垃圾回收 → watcher 不工作
- 没有 `$.global.__INSTALLED__` 检查 → 脚本被 eval 多次时会注册多个 idle task
- idle task 的 `sleep: 1000` 是最小间隔，实际触发频率受 InDesign 主线程空闲程度影响

### 5.5 参数传递机制

**`app.scriptArgs`（当前方案，有竞态问题）：**

```
// dispatch.jsx 设置
app.scriptArgs.setValue("pipeline_batch_mode", "true");
app.scriptArgs.setValue("pipeline_input_json", "/path/to/output.json");
app.scriptArgs.setValue("pipeline_output_indd", "/path/to/result.indd");

// templateA.jsx 读取
var batchMode = app.scriptArgs.getValue("pipeline_batch_mode");
var inputJson = app.scriptArgs.getValue("pipeline_input_json");
```

**问题：** `app.scriptArgs` 是进程级全局变量。若多文档连续处理时某一步异常，后续脚本可能读到脏参数。

**重构建议：**
- 改为将参数写入临时 JSON 文件，脚本从文件读取
- 或在 `$.evalFile` 前通过函数显式传参（ExtendScript 中可定义全局函数）

### 5.6 `$.evalFile` 调用链

```
$.evalFile(scriptFile)
  └── 在当前引擎中同步执行目标文件
  └── 被 eval 的脚本不创建新引擎
  └── 被 eval 的脚本中的 #target / #targetengine 指令被忽略
  └── 可以访问调用者的全局变量和函数
```

这使得：
- dispatch 调用 template 时，template 中的 `#target "InDesign"` 被忽略（无关紧要）
- templateB/C/D 调用 templateA 时，通过 `app.scriptArgs` 传 `pipeline_force_layout_mode` 切换模式
- 所有脚本共享 InDesign 的 `app` 对象

### 5.7 InDesign 2026 特殊性问题

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| `#target "InDesign"` 导致脚本静默失败 | 清理 Adobe 组件时移除了 BridgeTalk/ExtendScript 通信层，`#target` 解析失败 | 移除该指令（已执行） |
| Startup Scripts 偏好设置丢失 | Adobe 更新或偏好重置可能关闭"启用启动脚本" | 安装脚本后需重启 InDesign 验证；若仍不执行，检查首选项 |
| AppleScript `do script` 始终可用 | 这是 macOS 级别的脚本接口，不依赖 ExtendScript 组件 | 可作为 watcher 失效时的备用方案 |

### 5.8 JSX 重构标准

#### 5.8.1 移除 `#target` 指令
- 所有 `.jsx` 文件 **不得包含** `#target "InDesign"` 或任何 `#target "InDesign-*"`
- 理由：InDesign 2026 中此指令导致脚本被静默跳过，且 Startup Scripts / `$.evalFile` 场景下此指令无意义

#### 5.8.2 `#targetengine` 使用规范
- **watcher 必须使用** `#targetengine "autoRainbowWatcherEngine"`（idle task 需要持久化引擎）
- dispatch 和 template 脚本 **不使用** `#targetengine`（通过 `$.evalFile` 在调用者引擎中执行）
- 引擎名应使用项目级命名空间前缀（如 `autoRainbow_xxx`），避免与用户其他脚本冲突

#### 5.8.3 参数传递规范
- **禁用** `app.scriptArgs` 作为跨脚本参数传递方式（有竞态）
- 改为 Rust 后端写入 `_pipeline_params.json` 到 JSX 同目录，JSX 从该文件读取
- 参数文件内容：
  ```json
  {
    "project_root": "/path/to/autoRainbow",
    "templates_root": "A_templates",
    "input_json": "/path/to/output.json",
    "output_indd": "/path/to/result.indd",
    "force_layout_mode": null
  }
  ```
- templateB/C/D 在调用 templateA 前更新此文件的 `force_layout_mode` 字段

#### 5.8.4 代码结构规范
- templateB/C/D 的薄封装模式（~23行）是合理的，保留此结构
- templateA 核心引擎（2467行）应考虑按功能拆分为多个文件（如 `layout-engine.jsxinc`）
- dispatch（759行）已包含进度 UI 和链接更新，后续可考虑拆分
- 所有配置项从 JSON 读取，代码中不出现硬编码数值

#### 5.8.5 错误处理规范
- 所有 InDesign 操作需 try-catch 包裹
- 错误信息使用 `formatError()` 模式（包含错误号、文件名、行号）
- 关键步骤记录日志（通过 writeLog / writeln）

#### 5.8.6 调试指引
- Watcher 日志：`workspace/B_outputs/logs/watcher.log`
- Dispatch 日志：`workspace/B_outputs/logs/dispatch.log`
- 手动测试：用 AppleScript `do script` 执行单个 JSX 文件
- 临时测试脚本：在 Startup Scripts 目录放简单 writeFile 脚本验证启动脚本机制是否正常

## 十、重构标准与规范

### 9.1 架构原则

1. **路径可配置化**：所有硬编码路径改为相对路径 + 配置文件，支持通过环境变量或配置文件指定 PROJECT_ROOT
2. **模块解耦**：Python 解析、InDesign 排版、Tauri 前端应职责清晰，通过 JSON 文件/标准接口通信
3. **增量安全**：不毁坏性清空输出目录，支持增量处理

### 9.2 目录与命名规范

| 项目 | 规范 |
|------|------|
| 板块目录名 | 保留中文名（如 `1_本周头条`），通过配置维护排序和显示 |
| 文件路径 | 统一使用正斜杠 `/`，所有路径基于 PROJECT_ROOT 计算，Rust 后端处理平台差异 |
| JSX 脚本 | 移除 `#target "InDesign"`，适当场景使用 `#targetengine` |
| 配置字段 | 统一 snake_case，清理拼写错误（`divde` → `divide`） |

### 9.3 配置规范

- 全局配置至少包含：所有目录的相对路径、模板映射表、默认排版参数
- 板块配置继承全局配置，支持覆盖
- 配置变更无需重启流水线

### 9.4 错误处理规范

- 单篇文档失败不阻塞整批
- 单板块模板异常不阻塞其他板块
- 所有异常必须有日志（统一 JSON 格式），且可追溯
- 图片缺失：跳过并记录，不中断

### 9.5 排版引擎规范

- 移除 `gapY` 等硬编码值，全量从配置读取
- 分页参数（soft/hard）统一语义清晰
- 所有原型框 label 通过配置指定，不改代码即可适应新模板
- 多线程/多脚本实例需避免 `app.scriptArgs` 竞争

### 9.6 日志规范

- 统一 JSON Lines 格式：`{"time": "ISO8601", "level": "INFO|WARN|ERROR", "module": "...", "message": "...", "extra": {...}}`
- 每篇文档处理有 start/end 配对日志
- 失败日志包含：板块、文档名、失败步骤、异常堆栈
- watcher.log 不被清空，按日期轮转

### 9.7 前端规范

- 后端命令参数从硬编码改为配置传递
- UI 状态持久化使用标准序列化，带版本字段
- 轮询间隔可配置
- 移除调试热键（F9/F11/F12），仅开发模式启用

### 9.8 测试保障

- Python 解析：对每个板块类型至少有一个测试 docx 和对应的期望 output.json
- JSX 排版：提供独立测试模板 `.indd`，验证原型框定位和分页行为
- Rust 后端：关键命令应有单元测试
- 端到端：提供自动化脚本验证完整流水线
